# FLOF Post-Audit Hardening Design

**Date:** 2026-07-24
**Status:** Proposed for implementation
**Scope exclusion:** VNPay is a simulation in this project and is explicitly excluded from this hardening pass.

## 1. Goal

Resolve the remaining actionable findings in `AUDIT_REPORT.md` without changing
the current modular-monolith architecture, deleting data, resetting the
database, running destructive migrations, or exposing secrets.

The completed work must leave the repository with:

- patched production dependencies or an explicit documented residual risk;
- reliable email delivery state and retry behavior;
- production-safe rate limiting for sensitive endpoints;
- audit logging for administrator mutations;
- bounded and validated pagination;
- a stricter production CSP;
- reproducible runtime/deployment documentation;
- integration-focused regression tests for the changed behavior;
- updated audit documents that reflect the verified result.

## 2. Non-goals

- Do not modify, exercise, or certify VNPay callback/payment verification.
- Do not introduce microservices.
- Do not change the Prisma data model unless implementation evidence proves a
  schema change is necessary. The planned work does not require one.
- Do not run `prisma migrate`, `prisma db push`, `prisma db seed`, database
  reset, or destructive data commands.
- Do not add a new observability vendor or hosted infrastructure.
- Do not redesign the storefront or admin UI.
- Do not commit, stage, or overwrite unrelated user changes.

## 3. Delivery strategy

Work proceeds through four independently verifiable gates. A gate is complete
only after its targeted regression tests pass. The final release gate runs the
entire project verification suite.

### Gate 1 — Dependency and reliability blockers

#### Dependency upgrades

Inspect the current npm advisory graph and upgrade only the packages required
to remove production Critical/High advisories. Do not run
`npm audit fix --force`. Prefer compatible patched releases and keep the
existing Next.js 15/React 19/Auth.js v5 architecture.

If no patched compatible Auth.js release exists, document the exact advisory,
affected installed version, available version, and residual risk instead of
forcing a breaking or prerelease downgrade.

#### Email delivery contract

Change the internal email sender from a silent best-effort function to an
explicit delivery contract:

- missing provider configuration produces a typed delivery failure;
- provider exceptions propagate as delivery failures;
- success is returned only after the provider accepts the request;
- no secret, token, or full provider response is logged.

The outbox processor must:

- mark a record `SENT` only after confirmed delivery;
- mark a failed attempt `FAILED`, increment `retryCount`, and set
  `nextRetryAt`;
- reject unsupported outbox types as failures instead of marking them sent;
- preserve the existing maximum retry policy;
- avoid returning raw provider error details to the HTTP client.

Inline welcome/password-reset callers keep their user-enumeration-safe
responses. They may log a sanitized operational error, but must not expose
delivery details to the public response.

#### Production rate limiting

Keep memory limiting for local development and tests. For production:

- sensitive auth endpoints must not silently fall back to process-local memory;
- when the distributed store is missing or unavailable, the request is denied
  with a service-unavailable result rather than treated as allowed;
- public read endpoints may retain an availability-oriented memory fallback;
- logs must not include the Upstash token or request authorization header.

This behavior is expressed through an explicit failure policy instead of an
implicit `NODE_ENV` branch hidden inside callers.

## 4. Gate 2 — Governance and API hardening

### Audit log coverage

All state-changing administrator endpoints must write an audit event in the
same database transaction as the domain mutation whenever a Prisma
transaction exists.

Required domains:

- users and roles;
- articles;
- categories and suppliers;
- colors and collections;
- dealers;
- media metadata/action result;
- quotes and reviews;
- chat status/replies;
- product promotions;
- notification state changes.

Audit records contain only:

- actor ID and email;
- action name;
- entity type and entity ID;
- minimal before/after business fields;
- timestamp generated by the database.

They must never contain password hashes, OAuth tokens, API credentials, reset
tokens, authorization headers, or raw uploaded file content.

Where an external side effect cannot share a Prisma transaction (Cloudinary),
record a successful audit event only after the provider confirms the action.
Failed external actions remain operational errors and are not recorded as
successful mutations.

### Pagination validation

Create one shared parser for page/limit query parameters:

- defaults: page 1, limit 20;
- page must be a positive integer;
- limit must be an integer from 1 through 100;
- invalid values return HTTP 400;
- response metadata keeps the existing shape.

Apply it to products, blogs, colors, dealers, and admin notifications. Existing
unpaginated calls remain backward compatible where current UI relies on a full
list; the parser is used whenever pagination parameters are supplied.

### API status semantics

Authenticated users without the required admin/staff role receive HTTP 403.
Unauthenticated requests continue to receive HTTP 401. No broad response-shape
rewrite is included in this pass.

## 5. Gate 3 — Browser and deployment hardening

### Content Security Policy

Use separate development and production policies:

- production removes `unsafe-eval`;
- required image, map, worker, font, and API origins remain explicitly listed;
- `unsafe-inline` for styles/scripts is removed only where the current Next.js
  rendering path can build successfully without it;
- if nonce support is required for scripts, implement it centrally rather than
  weakening individual routes;
- preserve HSTS, frame, referrer, MIME, and permissions headers.

The build and a local smoke test must prove that the selected policy does not
break route generation. CSP tightening is not considered complete from a
string assertion alone.

### Runtime reproducibility

Add one supported Node runtime declaration shared by local development, CI,
and deployment. The package engine and GitHub Actions version must agree.

### Deployment runbook

Document:

- required environment variable names without values;
- pre-deploy quality gates;
- migration status and deploy ordering;
- cron endpoint scheduling and authentication;
- rate-limit dependency health;
- rollback steps for application and migration failures;
- Neon backup/PITR verification checklist;
- post-deploy smoke checks and alert conditions.

No production service is changed by this document-only work.

### ERD

Replace the stale ERD source with a text-based Mermaid ERD generated from the
current Prisma model boundaries. The PNG may remain as a historical artifact
only if clearly marked stale; the Mermaid source becomes the maintained
reference.

## 6. Gate 4 — Tests and verification

### Test-first requirements

Each behavior change starts with a failing regression test:

1. email sender reports missing configuration/provider failure;
2. outbox does not mark failed or unsupported delivery as sent;
3. sensitive production rate limiting denies when the distributed store is
   unavailable;
4. pagination rejects invalid/oversized input;
5. authorization helper distinguishes 401 from 403;
6. audit payload sanitizer excludes sensitive fields;
7. production CSP omits `unsafe-eval`;
8. runtime declarations are consistent.

Tests should exercise extracted pure functions/services directly. Route-level
tests may use dependency injection where database/provider access cannot be
performed safely. Do not add test-only branches to production code.

### Final verification

Run in this order:

1. targeted regression tests after each red/green cycle;
2. `npm run lint`;
3. `npm run build`;
4. `npm run typecheck`;
5. `npm test`;
6. `npx prisma validate`;
7. `npm run db:status`;
8. `npm audit --omit=dev --audit-level=high`.

The build is run before the standalone typecheck so generated Next.js type
artifacts are current. A failing dependency audit is reported honestly with
the exact remaining advisory and is not hidden by changing the audit level.

## 7. Error handling and safety

- Public auth responses do not disclose whether an email account exists.
- Provider and infrastructure errors are sanitized before reaching clients.
- Logs identify the failing subsystem but never print secret values.
- All commands remain non-destructive.
- Existing untracked `.ai-understand/` data and audit documents are preserved.
- Source changes are limited to the files required by these gates.

## 8. Acceptance criteria

The implementation is accepted when:

- all non-VNPay Critical/High findings are fixed or have a precise residual-risk
  record when no compatible patch exists;
- outbox state matches actual delivery outcome;
- sensitive production endpoints cannot silently use local-only rate limits;
- administrator mutations in scope produce sanitized audit events;
- invalid pagination returns 400 and cannot request more than 100 records;
- production CSP no longer contains `unsafe-eval`;
- Node runtime declarations match;
- ERD and deployment runbook reflect the current source;
- all targeted and full verification commands complete with recorded results;
- `AUDIT_REPORT.md` and the three audit-pack documents are updated with the new
  verified status;
- no VNPay source or test file is changed.
